# Apple Silicon macOS packaged release research

Research date: 2026-10-04. Checkout inspected: `prototype/study-release`, baseline `a43edd2` (`origin/main`). Scope: research only; the separate packaging spike supplies artifact evidence. This document does **not** establish that OutLoud can be packaged, notarized, or record audio successfully.

## Decision proposed for the release spec

**Recommendation:** pursue one Apple Silicon build with a production React renderer, an app-owned **PyInstaller `onedir` Python backend**, a pinned bundled FFmpeg executable, and **guided installation/reuse of independently owned Ollama**. Keep model weights outside the installer and require download consent. Treat a bundled standalone Python distribution as a fallback if the frozen dependency graph cannot pass the gates below. Do not embed Python into Electron's process for this milestone.

This is a proposed route, conditional on the packaging spike and real-device validation. Do not commit the implementation spec to a successful packaging outcome before those results exist.

The confirmed product boundaries come from [release-design.md](../release-design.md): small tester audience; Apple Silicon first; Study home, Resume studying and revision priorities; ordinary Chat; one shared focused voice/text composer; answer-specific, honest provisional/reference-supported feedback; subjects and manual topic creation usable before model setup; preserved desktop data and tested upgrades; no browser data import, Intel validation or automatic updates; signing/notarization before nontechnical distribution. Study terminology remains governed by [GLOSSARY.md](../../GLOSSARY.md).

Evidence labels used here:

- **Verified:** observed repository code, official documentation or upstream source. It establishes the stated API/build behavior, not OutLoud's integration success.
- **Recommendation:** a design choice inferred from those facts and the confirmed scope.
- **Unvalidated:** needs a build, integration test, real device or human action.
- **Human-only:** account/credential decisions, system consent and physical-device checks that documentation cannot complete.

## Current desktop and backend constraints

**Verified in the checkout:** [desktop main](../../apps/desktop/src/main.ts) uses development origin `http://127.0.0.1:5174`, repository `.venv/bin/python -m outloud`, and explicit `~/Library/Application Support/OutLoud` user data. Its [backend process controller](../../apps/desktop/src/backend-process.ts) refuses an occupied backend port, authenticates readiness with an owner token, maintains the parent stdin lease, drains accepted work and limits forced shutdown to its owned process tree. [ADR 0002](../adr/0002-desktop-backend-and-data-ownership.md) requires this private backend and separate desktop store; Ollama is a different, independently owned service. [Desktop README](../../apps/desktop/README.md) explicitly describes the build as development-only and the native microphone checks as incomplete.

The [desktop package](../../apps/desktop/package.json) declares Electron `^42.0.0`, TypeScript `~6.0.2`, Vite `^8.3.0`, and development/test tooling; its build currently compiles main/preload TypeScript, with no installer configuration. [.python-version](../../.python-version) pins Python 3.11. The [backend manifest](../../pyproject.toml) and [uv.lock](../../uv.lock) include Whisper `20250625`, torch `2.14.1`, sounddevice `0.5.6`, NumPy `2.4.6`, SciPy `1.17.1`, numba `0.68.0`, llvmlite `0.50.0`, cffi `2.1.1`, tiktoken `0.14.0`, Quartz/PyObjC `12.2.2`, pypdfium2 `5.13.0`, FastAPI `0.142.2`, and uvicorn `0.54.0`. These are repository version observations, **not confirmation of usable arm64 wheels, hook support or signed runtime compatibility**. Audit the entire locked closure, including PDF extraction and native resource files, rather than only torch and PortAudio.

[Transcription](../../src/outloud/transcription.py) lazily loads Whisper `base` on the first queued recording, using the upstream default cache and CPU/default-device selection, then transcribes with `fp16=False`. [Chat](../../src/outloud/chat.py) calls local `127.0.0.1:11434`, uses `gemma3:4b`, and still offers terminal commands in failure messages. Those messages and the hidden first-recording model download must change for a no-terminal tester experience.

## Production renderer and native payload

**Verified:** Electron's ASAR support is a virtual filesystem. Executing binaries within ASAR is supported by `execFile`, not the existing `spawn` path; native APIs may extract files temporarily, and unpacked files must accompany the archive. Python and FFmpeg cannot be assumed to understand Electron's virtual paths. [Electron ASAR documentation](https://www.electronjs.org/docs/latest/tutorial/asar-archives).

**Recommendation:** package compiled main/preload/control pages and `vite build` renderer assets; place the entire backend executable/native dependency tree and FFmpeg on the real filesystem outside `app.asar`. Resolve their paths from the packaged app, never the checkout, shell activation or a user's Homebrew installation. Preserve stdin ownership and console-style backend stdio even though users launch a GUI. Keep immutable code in the signed bundle, and databases, recordings, model downloads and logs in writable per-user locations.

For the narrow first build, prefer an Electron-owned loopback static server for production assets at the existing desktop origin `http://127.0.0.1:5174`. It should serve only packaged files, reject path traversal, fail clearly on port conflict and close with the app; it is **not Vite**. This preserves the existing origin-dependent profile data and backend allowlist with fewer changes. Validate this choice against the spike. An alternative is a secure custom app protocol; Electron recommends custom protocols over `file://`, and exposes registration for standard/secure/fetch-capable schemes. [Electron security guidance](https://www.electronjs.org/docs/latest/tutorial/security#18-avoid-usage-of-the-file-protocol-and-prefer-usage-of-custom-protocols), [protocol API](https://www.electronjs.org/docs/latest/api/protocol).

Changing origin requires explicit handling of draft recovery, selected conversation/subject and backend HTTP/WebSocket origin validation. Do not fix it by allowing every origin or blanket `Origin: null`. Preserve node integration off, context isolation, renderer sandboxing, navigation/pop-up restrictions, main-frame IPC checks, and the renderer's lack of the backend owner token. These requirements follow the existing [main](../../apps/desktop/src/main.ts), [backend URL configuration](../../apps/web/src/lib/backend-url.ts), [conversation recovery](../../apps/web/src/lib/conversations.ts), [chat recovery](../../apps/web/src/lib/chat-recovery.ts), and [server origin checks](../../src/outloud/server.py). A successful static page load alone does not verify those contracts.

Electron Forge supplies signing/notarization configuration and a DMG maker. Its Vite plugin is marked experimental, so adopting that plugin is optional; the existing renderer can be built separately and staged by the packager. Pin whichever build tooling the spike validates. [Forge signing](https://www.electronforge.io/guides/code-signing/code-signing-macos), [DMG maker](https://www.electronforge.io/config/makers/dmg), [Vite plugin](https://www.electronforge.io/config/plugins/vite).

## PyInstaller versus a bundled Python distribution

| Route | Verified basis | Recommendation and unvalidated cost |
| --- | --- | --- |
| PyInstaller `onedir` | Bundles the interpreter and dependencies; folder mode avoids `onefile`'s temporary extraction and extra bootloader process. [Operating modes](https://pyinstaller.org/en/stable/operating-mode.html) | First candidate. Inspectable native tree and simpler ownership/stdio behavior; still must prove imports, data resources, native loads, permissions and signing. |
| PyInstaller `onefile` | Extracts support files into a temporary directory before execution. [Operating modes](https://pyinstaller.org/en/stable/operating-mode.html#how-the-one-file-program-works) | Defer: large torch payload, repeated extraction and an additional process complicate launch/permission/lifecycle diagnosis. No first-release benefit established. |
| Bundled standalone Python + installed packages | Astral's project produces Python distributions with minimized runtime dependencies, Apple ARM targets and `install_only` archives. [Project overview](https://github.com/astral-sh/python-build-standalone/blob/main/docs/index.rst), [distribution/runtime guidance](https://github.com/astral-sh/python-build-standalone/blob/main/docs/running.rst) | Fallback: ship a pinned interpreter, stdlib, native wheels and OutLoud in an immutable tree, spawn it directly. Prove relocatability, module paths, dylib paths and signing; copying the development `.venv` is not this design. No pip/uv/downloaded executable installation on the tester machine. |
| CPython embedded inside Electron | Python's embedding API initializes an interpreter within another native application's process. [CPython embedding](https://docs.python.org/3/extending/embedding.html) | Defer: adds native integration and changes ADR 0002's process isolation/lifecycle seam. Bundling an interpreter subprocess should not be confused with in-process embedding. |

**Verified:** PyInstaller supports `arm64` targets, validates extension architecture, rewrites native library paths and re-signs collected binaries; Developer ID identity and entitlements can be supplied. Validation of Python extensions does not guarantee every dependent dylib is compatible. [macOS feature notes](https://pyinstaller.org/en/stable/feature-notes.html#macos-multi-arch-support).

With library validation enabled, an ad-hoc/no-Team-ID dylib can fail in a Developer ID process. **Recommendation:** sign the backend and its native closure consistently with the release identity and verify actual loads before considering a library-validation exception. [PyInstaller code-signing notes](https://pyinstaller.org/en/stable/feature-notes.html#macos-binary-code-signing).

Upstream contributed hooks collect torch data/submodules/native libraries and sounddevice's `_sounddevice_data/portaudio-binaries/libportaudio*` payload. This is evidence of hook machinery, **not proof that the exact locked versions work**. [Torch hook](https://github.com/pyinstaller/pyinstaller-hooks-contrib/blob/master/_pyinstaller_hooks_contrib/stdhooks/hook-torch.py), [sounddevice hook](https://github.com/pyinstaller/pyinstaller-hooks-contrib/blob/master/_pyinstaller_hooks_contrib/stdhooks/hook-sounddevice.py). Sounddevice documents automatic PortAudio installation for pip on macOS; freezing must retain that library instead of finding a developer-machine copy. [Official installation source](https://github.com/spatialaudio/python-sounddevice/blob/master/doc/installation.rst).

**Recommendation:** build natively on Apple Silicon, explicitly target arm64, pin Python/PyInstaller/hooks and locked dependencies, retain the build manifest and checksums, and inspect every shipped Mach-O with architecture/dependency tools. No unresolved references to `.venv`, repository paths or `/opt/homebrew` are acceptable. Exercise numba/LLVM and tokenizer/PDF resources, not just `import torch`. Keep the existing CPU Whisper path initially; Apple Silicon does not imply the current code uses MPS. Upstream Whisper defaults to CUDA if available, otherwise CPU. [Pinned Whisper loader](https://github.com/openai/whisper/blob/v20250625/whisper/__init__.py).

Whisper's audio loader invokes the `ffmpeg` executable via a subprocess. Bundle a pinned arm64 FFmpeg and set the backend's private executable search path (or change to an explicit executable path); Finder launch must not depend on shell PATH. [Pinned audio loader](https://github.com/openai/whisper/blob/v20250625/whisper/audio.py). The exact FFmpeg build, linked libraries, size, minimum macOS version and signing remain spike outputs.

## Signing, entitlements and microphone attribution

**Verified:** notarization requires valid Developer ID signatures on executables, hardened runtime, secure timestamps, appropriate entitlements, and no enabled `get-task-allow`. Notarization is an automated security check, not functional testing or App Review. [Apple notarization requirements](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution).

Apple documents nested-code locations, signing inside-out and the hazards of using `codesign --deep` as a signing strategy. **Recommendation:** enumerate Python extensions, torch/LLVM/PortAudio/PDF dylibs, FFmpeg and Electron helpers; settle their bundle layout before sealing the outer `.app`; verify each signature after any path rewriting. A resource-tree staging layout from the spike is not automatically the final nested-code layout. Do not blindly recursively sign unrelated data files. [Apple TN2206](https://developer.apple.com/library/archive/technotes/tn2206/_index.html).

Use distinct, minimal executable entitlement sets. Electron's notarization guidance requires JIT support and advises against adding unsigned-executable-memory for modern Electron. Python/numba/LLVM may have different executable-memory requirements; **those must be measured under hardened runtime**, not solved by copying every Electron entitlement or disabling library validation wholesale. [Electron notarize guidance](https://github.com/electron/notarize#prerequisites). Forge supports per-file entitlement selection. [Forge entitlement configuration](https://www.electronforge.io/guides/code-signing/code-signing-macos#customizing-entitlements).

For microphone capture, set a stable OutLoud bundle identifier and `NSMicrophoneUsageDescription` in the final app. Electron's `askForMediaAccess('microphone')` requests consent, and previously denied access requires Settings/restart handling. [Electron permission API](https://www.electronjs.org/docs/latest/api/system-preferences#systempreferencesaskformediaaccessmediatype-macos). Hardened runtime's `com.apple.security.device.audio-input` permits Core Audio input; ensure the actual capturing backend executable has the required entitlement, with the final signed process chain inspected. Chromium's renderer sandbox and macOS App Sandbox are separate concepts; this direct Developer ID release need not introduce Mac App Store sandboxing. [Apple audio input entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.device.audio-input).

**Unvalidated:** Electron consent may or may not be attributed correctly to the Python/PortAudio child. Apple's DTS explains that responsible-app attribution for helpers uses heuristics and can be broken by process behavior; that discussion concerns general TCC/file permissions and is not a microphone guarantee. [DTS: On File System Permissions](https://developer.apple.com/forums/thread/678819). The current launcher uses `detached: true` for owned process-group shutdown; specifically test whether this launch topology affects attribution. Do not change its process ownership merely on the assumption that detached launch is harmless or harmful.

**Human-only hard gate:** install the final signed app from a quarantined download, launch via Finder, and actually record recognizable speech with sounddevice. Confirm the permission prompt and Settings entry identify OutLoud, the WAV is nonempty/playable, transcription arrives in the initiating conversation, denial/recovery works, and closing during transcription drains correctly. Repeat for a new macOS user and a replaced app build with the same signing identity. Mocked Electron API tests, an ad-hoc signature, permission status `granted`, or a successful backend health response do not satisfy this gate. If attribution fails, test a properly bundled/signed helper or a revised launch chain before considering a larger native capture redesign.

## Developer ID credentials and DMG distribution

**Human-only prerequisites:** an Apple Developer Program membership; an authorized person to create/access a **Developer ID Application** certificate and its matching private key; stable team/bundle identity; and a supported Xcode/notarytool environment. Apple's certificate creation page specifies Account Holder access, with a separate cloud-managed access option. A `.cer` without the corresponding signing private key is insufficient. **Developer ID Installer** signs installer packages, not an ordinary drag-to-Applications DMG. [Apple certificate types/access](https://developer.apple.com/help/account/certificates/create-developer-id-certificates/), [Electron signing prerequisites](https://www.electronforge.io/guides/code-signing/code-signing-macos#prerequisites).

Notary authentication is separate from the signing identity: use an Apple ID + app-specific password + Team ID, or an appropriate App Store Connect API key with its required identifiers. A Keychain credential profile is supported; do not put credentials in source, the shipped app or logs. The Electron notarize docs also distinguish newer individual API keys from team keys, so pin the credential method to the installed tooling. [Apple custom workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow), [Electron notarize authentication](https://github.com/electron/notarize#api).

**Recommendation:** sign the complete app inside-out; verify it; create/sign the DMG with Developer ID Application; submit the final DMG with `notarytool`; inspect the returned log; staple and validate the tickets for the app and DMG; retain checksums and the notarization submission ID. Apple accepts disk images and generates tickets for nested items; stapling allows offline Gatekeeper verification, whereas ZIPs cannot themselves be stapled. Do not alter executable/resource content after signing. [Apple custom notarization workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow), [Apple disk-image signing guidance](https://developer.apple.com/library/archive/technotes/tn2206/_index.html#//apple_ref/doc/uid/DTS40007919-CH1-TNTAG18).

**Unvalidated distribution gate:** download the actual release DMG on a clean supported Apple Silicon Mac, retain quarantine, install into Applications, disconnect from the network and open through Finder. Verify Gatekeeper acceptance, renderer, backend, microphone and later model setup. No disabling Gatekeeper, removing quarantine, terminal dependency installation or developer-machine cache fallback belongs in the tester instructions. An unsigned build is useful only as internal spike evidence.

## Ollama: reuse and guided external installation

**Verified:** official macOS instructions currently require Sonoma 14+ and support Apple M-series CPU/GPU. The documented GUI route mounts `ollama.dmg`, drags the app into Applications and launches it; first launch may request permission for a CLI symlink. This route does not require terminal commands. [Ollama macOS instructions](https://docs.ollama.com/macos), [official Mac download](https://ollama.com/download/mac). **Recommendation:** provisionally target macOS 14+; raise that minimum if any chosen native payload requires it. Hardware memory/disk suitability remains measured, not inferred from CPU support.

| Option | Proposed ownership and tradeoff |
| --- | --- |
| Guided external Ollama — recommended | Probe existing service first. If missing, open the official download in the default browser, show native installation/launch instructions and Retry detection. Explain any external permission prompt. Ollama, configuration, process and model cache remain user-owned; OutLoud manages only its API requests. |
| Private bundled Ollama — defer | Would need a pinned complete runtime/native library/Metal payload, separate app-owned model path and loopback port, signatures/notarization, security/upgrade responsibility and process ownership proof. This is a possible future design, not proven feasibility. Never acquire a preexisting listener or kill a conflicting process. |

The upstream Darwin build script packages more than one executable and includes native libraries/Metal assets and license/notice payloads. Bundling a single copied `ollama` command is therefore not an established complete distribution. [Pinned Darwin packaging source](https://github.com/ollama/ollama/blob/42e911bc3d05798cad729cb474bf62f378cb2e26/scripts/build_darwin.sh).

**Recommendation:** use bounded loopback HTTP probes to `/api/version` and `/api/tags`, validate response shape and test a supported runtime range. Distinguish no service, unrelated/incompatible listener, installed-but-not-running app, absent model and generation failure. Ollama documents a local API at port 11434; version returns the runtime version and tags returns available models with digests/sizes. A listening port does not prove identity, ownership or compatibility, and Ollama's API is not strictly versioned. [API introduction](https://docs.ollama.com/api/introduction), [version endpoint](https://docs.ollama.com/api-reference/get-version.md), [available models](https://docs.ollama.com/api/tags).

Never stop/restart a reused Ollama service on OutLoud exit, change its environment/launch configuration, disable its cloud settings globally, replace its application, uninstall it, unload another client's models or delete its cache. Ask users to open their installed app if it is stopped. Default macOS models live under `~/.ollama/models`, but users can configure a different directory; use APIs instead of assuming paths. [Ollama model storage/configuration](https://docs.ollama.com/faq#where-are-models-stored). Pull only after explicit consent; an existing usable model should be reused without silently refreshing its tag. Pull source can rewrite manifests and prune unused layers, so pulling is a shared-cache mutation, not a harmless availability check. [Pinned model pull source](https://github.com/ollama/ollama/blob/42e911bc3d05798cad729cb474bf62f378cb2e26/server/images.go#L1027-L1155).

**Verified caveat:** localhost is not proof of local inference. Ollama supports cloud models through its local API, and source includes `remote_model`/`remote_host` and upstream routing. **Recommendation:** allow only the tested local model, inspect remote metadata where supported, and verify generation offline. Do not accept missing metadata on an older runtime as proof of locality. [API introduction](https://docs.ollama.com/api/introduction), [pinned model response types](https://github.com/ollama/ollama/blob/42e911bc3d05798cad729cb474bf62f378cb2e26/api/types.go#L742-L760), [pinned routing](https://github.com/ollama/ollama/blob/42e911bc3d05798cad729cb474bf62f378cb2e26/server/routes.go).

### Downloads, cancellation and real readiness

**Verified:** `POST /api/pull` streams NDJSON by default with `status` and optional `digest`, `total`, `completed`. Progress is layer-oriented. Success has a terminal success status, and errors can arrive after HTTP headers. [Pull API](https://docs.ollama.com/api/pull.md), [streaming API](https://docs.ollama.com/api/streaming), [pinned streaming error handling](https://github.com/ollama/ollama/blob/42e911bc3d05798cad729cb474bf62f378cb2e26/server/routes.go#L2266-L2312).

**Recommendation:** keep setup in the backend with an app-owned operation ID and progress subscription; serialize/deduplicate OutLoud's pulls. Show named phases, per-layer byte counts and indeterminate verification/loading. Do not manufacture an overall percentage when the full total is unknown. Neither HTTP 200, one layer at 100%, nor stream EOF means ready. After terminal success, inspect the selected model and run a bounded inference check. Provide actionable network/disk/memory errors, Cancel, Retry and Later; do not automatically download after reopening.

Official repository docs say interrupted pulls resume and concurrent calls share progress. Pinned source ties a pull to request cancellation but keeps a shared blob download alive until its last reference is released. **Recommendation:** Cancel closes OutLoud's own request and stops its UI operation; preserve partial files and retry the same model. Explain that another Ollama client may keep shared network activity running. Do not kill the server or remove blobs to enforce cancellation. Exact disconnect timing, resume, competing clients and disk-full behavior remain integration gates. [Official pull documentation](https://github.com/ollama/ollama/blob/42e911bc3d05798cad729cb474bf62f378cb2e26/docs/api.md#pull-a-model), [request context](https://github.com/ollama/ollama/blob/42e911bc3d05798cad729cb474bf62f378cb2e26/server/routes.go#L1245-L1302), [shared download cancellation](https://github.com/ollama/ollama/blob/42e911bc3d05798cad729cb474bf62f378cb2e26/server/download.go#L451-L527).

`/api/tags` proves availability; `/api/ps` reports loaded models; `/api/show` exposes details, capabilities and license. An empty request can preload a model, but none of those proves it can complete OutLoud's Study workload. [Loaded models](https://docs.ollama.com/api/ps), [model details](https://docs.ollama.com/api-reference/show-model-details), [preloading](https://docs.ollama.com/faq#how-can-i-preload-a-model-into-ollama-to-get-faster-response-times), [chat API](https://docs.ollama.com/api/chat).

**Recommendation:** track separate states for backend availability, Ollama compatibility, model downloaded, generation validated, Whisper downloaded/loaded and microphone permission/capture. After consent, run a synthetic Chat probe and a representative Study structured-response check with the existing schema validator, without sending saved learner content. Recheck when failures occur; a one-time green badge is not permanent readiness. Treat insufficient memory/loading failure as failure, not successful setup. Keep subject/topic creation and saved Study navigation usable throughout; disable only dependent actions with Complete setup guidance.

Whisper setup also needs consent. Its pinned loader defaults to `~/.cache/whisper`, verifies SHA-256, and downloads automatically when the checkpoint is absent/invalid; progress is terminal-oriented and its existing function does not provide OutLoud's cancellation UI. [Pinned Whisper loader](https://github.com/openai/whisper/blob/v20250625/whisper/__init__.py). **Recommendation:** omit Whisper weights as well as Gemma weights from the installer; offer a separate voice-model step with bytes, checksum verification, cancellable temporary download, atomic completion and retry. Store new downloads in an explicit app-owned model directory, reuse an existing trusted checkpoint only after validation, and load by validated path so the first recording cannot trigger a surprise download. Do not claim resumable Whisper downloads until implemented/tested. Test an actual decode/transcription before reporting voice ready.

## App-owned data and compatibility

**Verified:** the desktop backend writes relative to its user-data working directory: recordings, `recordings/conversations.sqlite3` and `recordings/delivery.sqlite3`. Conversations and Study share a connection; current upgrades use column detection and additive `ALTER TABLE`, not a central explicit schema-version protocol. Desktop profile storage also holds draft/reply recovery, conversation selection and subject selection. [Backend launcher](../../apps/desktop/src/backend-process.ts), [server](../../src/outloud/server.py), [conversation schema](../../src/outloud/conversations.py), [Study schema](../../src/outloud/study.py), [conversation/profile recovery](../../apps/web/src/lib/conversations.ts), [chat recovery](../../apps/web/src/lib/chat-recovery.ts), [Study selection](../../apps/web/src/components/study-area.tsx).

**Recommendations for the spec:**

1. Preserve `~/Library/Application Support/OutLoud` explicitly, existing database filenames/recording paths and the Electron profile. Installer replacement must not create an empty alternate library due to changed product/bundle name.
2. Preserve the existing desktop origin initially. If changed, export/import the known old-origin recovery keys through a controlled app migration and test draft conflicts, selected conversation and Study resume. Reusing the same `userData` directory alone does not prove origin-scoped recovery survives. Do not import browser-development data.
3. Before changing schemas, take a consistent backup of both stores and define supported schema versions, transactional/idempotent upgrades and refusal of unsupported newer schemas. Python's SQLite backup API supports consistent backups; avoid blindly copying a live database without coordinating its journals/connections. [Python SQLite backup](https://docs.python.org/3/library/sqlite3.html#sqlite3.Connection.backup).
4. Test fixtures from the current desktop schema with messages, unsaved drafts, transcription delivery, subjects, topics, revisions, uploads/reference approval, hinted evidence and provisional assessments. Verify reopened revision priorities and study progress as well as raw row counts. Test interrupted/failed upgrade, low disk, subsequent reopen and attempted downgrade; never silently reset on error. Preserve existing assessment semantics described in [Study design](../study-mode-design.md).
5. Keep app-owned model caches distinct from the preserved learner store; no automatic cleanup of user Ollama or shared Whisper directories. Uninstallation/replacement should leave learner data until an explicit future delete-data action is designed.
6. Extend owned-backend readiness to include executable/backend version and schema compatibility, retaining token authentication and the parent lease. Refuse unrelated port occupants. Preserve accepted-transcription draining and explicit loss warning before forced termination.

## Remaining hard gates before nontechnical release

All gates are **unvalidated by this research**. The packaging spike can supply some build evidence; only the final signed installer and real tester-device checks close distribution gates.

| Gate | Required evidence |
| --- | --- |
| Complete arm64 payload | Locked build manifest; complete native/resource inventory; minimum macOS version; architecture/dylib checks; reproducible build and measured DMG/disk size. No checkout/Bun/uv/system Python/Homebrew dependency at runtime. |
| Clean production launch | Installed app opens via Finder with an empty developer PATH; production renderer, HTTP/WebSocket, recovery and backend start/stop/reopen work; unrelated listeners are never attached to or killed. |
| Hardened native execution | Final signatures/entitlements and successful loading/execution of torch, LLVM/numba, PortAudio, PDF extraction, tokenization and bundled FFmpeg without broad unexplained exceptions. |
| Actual microphone/voice | OutLoud attribution and consent; deny/Settings recovery; real audio/transcript; correct conversation delivery; shutdown drain and explicit forced-loss path, including app replacement. |
| Consent/setup/readiness | No hidden weight download; Later works; model terms/bytes/disk requirements shown; progress/error/Cancel/Retry; real Chat + valid Study response + voice checks; offline local inference. |
| External Ollama ownership | Existing compatible service reused; existing model not refreshed without consent; absent/stopped/incompatible service and port conflict handled; competing pulls/cancel/resume tested; OutLoud exit never kills Ollama. |
| Preserved learner data | Populated current desktop fixture survives install/upgrade; profile recovery and Study resume remain; supported migrations/downgrade refusal tested; browser store stays separate. |
| Redistribution | Exact runtime/dependency notices, FFmpeg source/configuration and model-license handling approved by the release owner. No claim of clearance based only on upstream project names. |
| Signed/notarized installer | Developer ID/private key and notary credentials provisioned by an authorized human; accepted notary logs; stapled/validated app and DMG; quarantined download accepted by Gatekeeper on a clean Mac, including offline launch. |
| Tester usability | A nontechnical tester completes Applications install, manual subject/topic setup, later Ollama/model setup, Study resume/revision and ordinary Chat without source tools or terminal instructions. Feedback stays honestly provisional where appropriate. |

**Human-only work:** obtain signing/notary credentials and choose the distribution identity; respond to OS/external-installer consent; perform spoken-audio/permission checks; assess license obligations for the selected artifacts; run the nontechnical walkthrough. These are final evidence requirements, not reasons to postpone the research or internal build.

The release spec should select this narrow candidate, record spike measurements and any failed gates, and keep first-party backend ownership separate from user-owned Ollama. Documentation establishes available mechanisms; artifact and device evidence establish release readiness.
